# Codex Lab на двух машинах (UzCloud, Ташкент)

Один образ Docker (`Dockerfile` в корне), две машины, роль задаёт `ROLE`:

```
посетитель ──HTTPS──▶ codexlab-web  (1 vCPU / 2 ГБ, внешний адрес)
                      ├─ Caddy: сертификаты, адрес посетителя в X-Forwarded-For
                      │    ├─ адреса админки ──────────────┐   частная сеть
                      │    └─ остальное ─▶ сайт ROLE=web    │
                      │         страницы, заявки,           │
                      │         сайты клиентов              ▼
                      └───────────── база ─────────▶ codexlab-admin  (2 vCPU / 2 ГБ, только частная сеть)
                                                     ├─ сайт ROLE=admin: публикация из админки, совет
                                                     │   агентов, студия, бот, рассылки, доставка заявок
                                                     └─ PostgreSQL 18
```

- **Машина сайта** отвечает посетителям. Схему базы не меняет: при старте ждёт, пока её обновит машина
  админки (до 2 минут), и только потом открывает порт.
- **Машина админки** — всё фоновое и всё, что под паролем. О новой заявке или правке сайта клиента машина
  сайта сообщает ей через базу (`NOTIFY codexlab`), и заявка уходит в Telegram сразу, а не при следующем опросе.
- Тексты и цены сайта, сайты клиентов, заявки — в базе: обе машины видят одно и то же, общей папки нет.
  Папка данных у каждой машины своя — в ней только кэш курса доллара.

## Файлы

| Файл | Что |
| --- | --- |
| `compose.web.yml` | машина сайта: Caddy и сайт `ROLE=web` |
| `compose.admin.yml` | машина админки: PostgreSQL и сайт `ROLE=admin` |
| `Caddyfile` | какие адреса Caddy передаёт на машину админки; список сверяет проверка `tests/test_roles.py` |
| `compose.env.example` | адреса машин, пароль базы, домены — образец `/opt/codexlab/env/compose.env` |

Сеть у контейнеров — сеть машины (`network_mode: host`): порты открывает и закрывает `ufw`. Опубликованные
порты Docker обошли бы `ufw`, поэтому их нет.

| Машина | Открыто (`ufw`) |
| --- | --- |
| codexlab-web | 80, 443 — всем; 22 — для выкладки |
| codexlab-admin | 5432 и 8080 — только с частного адреса машины сайта; 22 — для выкладки |

Машине админки нужен выход в интернет (NAT): Telegram, курс NBU, IndexNow, Claude.

## Настройки

На каждой машине в `/opt/codexlab/env/` (права 600, владелец root):

- `compose.env` — по образцу `compose.env.example`: частные адреса обеих машин, пароль базы (`openssl rand -hex 24`:
  только буквы и цифры, он стоит в адресе базы), домены сайта;
- `app.env` — настройки сайта, как в `.env.example` в корне. `ROLE`, `HOST`, `PORT`, `DATABASE_URL`, `TRUST_PROXY`
  и `TRUSTED_PROXIES` задают compose-файлы — в `app.env` их не пишут.

| Настройка | Сайт | Админка |
| --- | --- | --- |
| `PUBLIC_URL`, `ORDER_RETENTION_DAYS`, `STUDIO_*`, `GOOGLE_SITE_VERIFICATION` и другие для поиска | да | да |
| `ADMIN_PASSWORD` | не нужен | да |
| `BOT_TOKEN`, `ADMIN_CHAT_IDS`, `ADMIN_USER_IDS`, `ANTHROPIC_API_KEY`, `INDEXNOW` | не нужны | да |

## Релиз

Порядок — всегда **сначала машина админки, потом машина сайта**:

```bash
# codexlab-admin
TAG=<версия> docker compose -f deploy/uzcloud/compose.admin.yml --env-file /opt/codexlab/env/compose.env up -d
# codexlab-web
TAG=<версия> docker compose -f deploy/uzcloud/compose.web.yml --env-file /opt/codexlab/env/compose.env up -d
```

Машина админки при старте доводит схему базы до своей версии; машина сайта ещё минуту-другую работает на
прежнем коде. Поэтому шаг схемы (`MIGRATIONS` в `app/db.py`) только добавляет — таблицы, столбцы со значением по
умолчанию — и не ломает прежний код. Убрать или переименовать столбец — в два релиза: сначала код перестаёт им
пользоваться, потом следующий шаг схемы его убирает.

Если машину сайта выложили первой, а схема старее её кода, сайт ждёт 2 минуты и выходит с понятной ошибкой;
Docker его перезапускает, и после выкладки машины админки он поднимается сам.

## Когда машина админки перезагружается

- Главная и страницы сайта продолжают открываться — с последними текстами и ценами, которые машина сайта успела
  прочитать (поле `site` в `/api/health` не меняется, в журнале — «база не отвечает»).
- Заявки, сайты клиентов, страницы хода работ и админка ждут базу и отвечают ошибкой, бот молчит.
- Вернулась база — всё восстанавливается само, перезапускать ничего не нужно.

## Команды

```bash
docker compose -f deploy/uzcloud/compose.admin.yml logs -f admin              # журнал
docker compose -f deploy/uzcloud/compose.admin.yml exec admin python -m app.site_versions   # публикации сайта
curl -s http://127.0.0.1:8080/api/health                                      # на машине сайта: роль, база, тексты
```

Проверено на стенде из контейнеров: машина сайта ждёт схему; заявка с сайта будит машину админки; публикация
из админки через Caddy видна на машине сайта; подменённый посетителем `X-Forwarded-For` не проходит; сайт клиента
из студии на машине админки открывается на машине сайта; без базы главная отвечает за миллисекунды.
