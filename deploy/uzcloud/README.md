# Codex Lab на двух машинах (UzCloud, Ташкент)

Один образ Docker (`Dockerfile` в корне), две машины, роль задаёт `ROLE`:

```
посетитель ──HTTPS──▶ codexlab-web  (1 vCPU / 2 ГБ / 20 ГБ, публичный адрес)
                      ├─ Caddy: сертификаты, адрес посетителя в X-Forwarded-For
                      │    ├─ адреса админки ──────────────┐   частная сеть
                      │    └─ остальное ─▶ сайт ROLE=web    │
                      │         страницы, заявки,           │
                      │         сайты клиентов              ▼
                      └───────────── база ─────────▶ codexlab-admin  (2 vCPU / 2 ГБ / 30 ГБ, только частная сеть)
                                                     ├─ сайт ROLE=admin: публикация из админки, совет
                                                     │   агентов, студия, бот, рассылки, доставка заявок
                                                     ├─ PostgreSQL 18
                                                     └─ копии базы ──▶ хранилище S3 UzCloud
```

- **Машина сайта** отвечает посетителям. Схему базы не меняет: при старте ждёт, пока её обновит машина
  админки (до 2 минут), и только потом открывает порт.
- **Машина админки** — всё фоновое и всё, что под паролем. О новой заявке или правке сайта клиента машина
  сайта сообщает ей через базу (`NOTIFY codexlab`), и заявка уходит в Telegram сразу.
- Всё, что нельзя потерять, — в базе: заявки, подписчики, проекты и сайты клиентов, тексты и цены сайта.
  Папка данных у каждой машины своя, в ней только кэш курса доллара. Копировать нужно только базу.

## Файлы

| Файл | Что |
| --- | --- |
| `bootstrap.sh` | подготовка чистой машины: Docker, файрвол, SSH по ключу, пользователь `deploy` |
| `release.sh` | выкладка версии на машину: запуск, ожидание здоровья, откат к прежней версии |
| `backup.sh` | копии базы в хранилище (ночью) и проверка восстановления (утром) |
| `compose.web.yml` | машина сайта: Caddy и сайт `ROLE=web` |
| `compose.admin.yml` | машина админки: PostgreSQL и сайт `ROLE=admin` |
| `caddy/Caddyfile` | какие адреса Caddy передаёт на машину админки; список сверяет проверка `tests/test_roles.py` |
| `../../.github/workflows/release.yml` | кнопка релиза: Actions → release → Run workflow |

На машинах всё лежит в `/opt/codexlab`: `deploy/` — эти файлы (их привозит кнопка релиза), `env/` — настройки
и пароли (права 700), `pg/` — база, `backup/` — три последние ночные копии и журнал копий.

Сеть у контейнеров — сеть машины (`network_mode: host`): порты закрывает `ufw`. Опубликованные порты Docker
обошли бы `ufw`, поэтому их нет.

| Машина | Открыто (`ufw`) |
| --- | --- |
| codexlab-web | 80, 443 — всем; 22 — для выкладки |
| codexlab-admin | 5432 и 8080 — только с частного адреса машины сайта; 22 — из частной сети |

## Первый запуск

**1. UzCloud.** Две машины Ubuntu 24.04 в одной частной сети. При создании вписать открытую часть ключа
выкладки (её пара — секрет `DEPLOY_SSH_KEY`). Публичный адрес сети — на машину сайта, порты 22, 80 и 443.
Машине админки нужен выход в интернет (NAT): Telegram, курс NBU, IndexNow, Claude, образы Docker. Хранилище
Object Storage — бакет `codexlab`.

**2. DNS (ahost).** Запись `A` для `new.codexlab.uz` — на публичный адрес. Без неё Caddy не получит сертификат,
и проверка снаружи не пройдёт.

**3. GitHub → Settings → Secrets and variables → Actions.**

| Где | Имя | Что |
| --- | --- | --- |
| секрет | `DEPLOY_SSH_KEY` | закрытый ключ выкладки (весь файл, с `-----BEGIN`) |
| секрет | `ADMIN_PASSWORD` | пароль админки, не короче 12 знаков |
| секрет | `BOT_TOKEN` | токен бота от @BotFather — когда бот будет; без него заявки только в базе |
| секрет | `S3_ACCESS_KEY`, `S3_SECRET_KEY` | ключи хранилища UzCloud |
| секрет | `BACKUP_PASSPHRASE` | пароль шифрования копий, не короче 20 знаков; **сохранить отдельно** — без него копию не открыть |
| секрет | `ANTHROPIC_API_KEY` | ключ Claude для студии — пока не нужен |
| переменная | `PROD_HOST` | публичный адрес сети (машина сайта) |
| переменная | `PROD_WEB_IP`, `PROD_ADMIN_IP` | частные адреса машин (10.…) |
| переменная | `PROD_DOMAIN` | адрес сайта: `new.codexlab.uz` (по умолчанию) или `codexlab.uz` после переезда |
| переменная | `PROD_KNOWN_HOSTS` | ключи машин — две строки, подскажет первый запуск в сводке |
| переменная | `S3_ENDPOINT` | адрес хранилища, например `https://s3.uzcstorage.uz`; `S3_BUCKET` — если бакет не `codexlab` |
| переменная | `ADMIN_CHAT_IDS`, `ADMIN_USER_IDS` | чаты и люди для заявок в Telegram (как в `.env.example`) |
| переменная | `PROD_BOOTSTRAP_USER` | пользователь образа для подготовки, если не `root` (тогда через `sudo`) |

Необязательные переменные — как в `.env.example`: `ORDER_RETENTION_DAYS`, `STUDIO_*`,
`GOOGLE_SITE_VERIFICATION`, `YANDEX_VERIFICATION`, `BING_SITE_VERIFICATION`. Пустое — значение по умолчанию.

**4. Кнопка.** Actions → release → Run workflow, ветка `uzcloud`, галочка «подготовить машины». Первый запуск
подскажет в сводке значение `PROD_KNOWN_HOSTS` — сохранить; дальше машины узнаются по ключам.

## Релиз

Actions → release → Run workflow, ветка — та, что выкладывается (до переезда — `uzcloud`, после — `main`).
Выкладывается последний коммит ветки, и только если на нём прошли автотесты.

1. Образ собирается в GitHub и загружается на обе машины; файлы выкладки и настройки из секретов — туда же.
2. Копия базы в хранилище с меткой `release`. Не снялась — релиз останавливается, ничего не тронуто.
3. **Машина админки**: база, схема, админка, копии в расписании.
4. **Машина сайта**: пароль базы переносится с машины админки (мимо журнала), сайт, Caddy перечитывает
   `Caddyfile`.
5. Проверка снаружи: страницы, роль `web`, адрес админки доходит до машины админки, на репетиции —
   заголовок `X-Robots-Tag: noindex` (поисковики не берут второй адрес).
6. Запись в Environments → production: следующий релиз покажет в сводке, какие PR вошли.

Не поднялась новая версия на машине — `release.sh` возвращает прежнюю, релиз красный. Машина админки
упала — машину сайта релиз уже не трогает.

Порядок — всегда сначала машина админки: она меняет схему базы, а машина сайта ещё минуту-другую работает на
прежнем коде. Поэтому шаг схемы (`MIGRATIONS` в `app/db.py`) только добавляет — таблицы, столбцы со значением
по умолчанию — и не ломает прежний код. Убрать или переименовать столбец — в два релиза.

## Копии базы

| Что | Когда | Где | Сколько |
| --- | --- | --- | --- |
| ночная копия | 03:40 по Ташкенту | `codexlab/db/codexlab-ГГГГ-ММ-ДД.dump.gpg`; три последние — и в `/opt/codexlab/backup` | 90 дней |
| перед релизом | каждый релиз | `codexlab/db/codexlab-ГГГГ-ММ-ДД-ЧЧММ-release.dump.gpg` | 90 дней |
| проверка восстановления | 05:10 | последняя ночная копия — из хранилища во временную базу без сети и сверка с боевой | — |

Копии зашифрованы (`gpg`, AES-256, пароль `BACKUP_PASSPHRASE`). Итог каждой копии и проверки — строкой в
`/opt/codexlab/backup/backup.log`, сбой начинается со слова `ОШИБКА`; без данных из базы. Проверить сейчас —
кнопка релиза с галочкой «проверить восстановление». Сигналы о копиях подключает мониторинг.

**Восстановление** (на машине админки):

```bash
cd /opt/codexlab/backup
gpg --decrypt codexlab-ГГГГ-ММ-ДД.dump.gpg > codexlab.dump          # спросит BACKUP_PASSPHRASE
C="docker compose -p codexlab -f ../deploy/compose.admin.yml --env-file ../env/compose.env"
$C exec -T db createdb -U codexlab restore_check                      # сначала — в пустую базу, посмотреть
$C exec -T db pg_restore -U codexlab --no-owner -d restore_check < codexlab.dump
# Вернуть в боевую — только при аварии: --clean заменяет всё, что в базе сейчас
$C stop admin
$C exec -T db pg_restore -U codexlab --no-owner --clean --if-exists -d codexlab < codexlab.dump
$C start admin
rm codexlab.dump
```

Копии старше трёх ночей — из хранилища (ключи — секреты `S3_*`): `aws --endpoint-url $S3_ENDPOINT s3 cp
s3://codexlab/codexlab/db/<файл> .`

## Переезд домена

1. Репетиция на `new.codexlab.uz`: релиз, проверить сайт, заявку, публикацию из админки, бота.
2. В день переезда: `uzcloud` сливается в `main`; переменная `PROD_DOMAIN` = `codexlab.uz`; в ahost записи
   `A` для `codexlab.uz` и `www.codexlab.uz` — на публичный адрес; релиз из `main`. Caddy получит сертификаты
   для обоих адресов, когда DNS начнёт указывать сюда (проверка ждёт до пяти минут). Заголовок `noindex`
   уходит сам, IndexNow включается сам.
3. Render выключить; через неделю — удалить.

## Когда машина админки перезагружается

- Главная и страницы сайта открываются с последними текстами и ценами, которые машина сайта успела прочитать.
- Заявки, сайты клиентов, страницы хода работ и админка ждут базу и отвечают ошибкой, бот молчит.
- Вернулась база — всё восстанавливается само.

## Команды на машине

```bash
cd /opt/codexlab/deploy
docker compose -p codexlab -f compose.admin.yml --env-file ../env/compose.env ps          # что запущено
docker compose -p codexlab -f compose.admin.yml --env-file ../env/compose.env logs -f admin
docker compose -p codexlab -f compose.admin.yml --env-file ../env/compose.env exec admin python -m app.site_versions
tail /opt/codexlab/backup/backup.log                                                     # копии
```

На машине сайта — то же с `compose.web.yml` (службы `web` и `caddy`).

Проверено на стенде из контейнеров: две машины Ubuntu 24.04 с systemd и SSH, хранилище S3, кнопка релиза —
шаги этого workflow как есть: подготовка машин, первый релиз, обновление, копия перед релизом, ночная копия
и проверка восстановления, откат сломанной версии, файрвол машины админки.
