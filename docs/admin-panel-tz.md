# Техническое задание: админ-панель Codex Lab

| | |
| --- | --- |
| Версия | 1.0, черновик на согласование |
| Дата | 04.11.2026 |
| Продукт | Codex Lab: сайт студии, Telegram-бот, студия white-label сайтов из 20 ИИ-агентов |
| Код | этот репозиторий (`app/`, `site/`), сервер на aiohttp + aiogram, базы SQLite |

Обозначения ролей в таблицах: **В** — Владелец, **М** — Менеджер, **Р** — Редактор, **Н** — Наблюдатель.
Требования без пометки входят в первую версию; с пометкой **(v2)** — делаются после неё.

---

## 1. Зачем нужна панель

Сейчас управление Codex Lab разнесено по трём местам, и у каждого свой вход:

| Где | Что умеет | Чего не хватает |
| --- | --- | --- |
| Встроенная админка сайта (`site/index.html`, «Вход для владельца») | контакты, тексты на RU/UZ/EN, цены, примеры, вопросы; публикация всей страницы по `ADMIN_PASSWORD` | истории версий и отката без SSH; только контент сайта |
| Страница совета `/council` | проекты студии, лента агентов, задачи, уроки | только просмотр: правки, оценки и проверка уроков делаются через бот или API |
| Команды бота для `ADMIN_CHAT_IDS` | `/last`, `/stats`, `/forget`, `/post`, `/subscribers`, `/studio`, `/lessons` | нет поиска, фильтров, статусов и истории; `/last` показывает только 5 последних заявок |

Что из-за этого плохо:

1. **Заявки никто не ведёт.** У них нет статусов, ответственных и заметок (в README прямо сказано: «Статусов заявок нет: заявки ведутся в Telegram»). Заявку старше пяти последних можно найти только в базе.
2. **Один общий пароль на всё.** `ADMIN_PASSWORD` открывает и публикацию сайта, и служебное API. Нельзя дать менеджеру доступ к заявкам без права менять сайт, нельзя понять, кто что сделал, нельзя отозвать доступ у одного человека.
3. **Лиды с сайтов клиентов и подписчики** видны только в виде сообщений в Telegram или числом.
4. **Откатить сайт** можно только по SSH, скопировав файл из `site/backups/`.
5. **Публикация передаёт всю страницу** (до 12 МБ), а сервер проверяет только `<!doctype html>` и наличие двух `id`.

**Цель:** одна защищённая веб-панель по адресу `/admin`, в которой владелец и команда ведут заявки, меняют сайт, управляют студией и рассылками, не заходя на сервер по SSH и не пользуясь общим паролем.

### 1.1 Как поймём, что цель достигнута

- Менеджер находит любую заявку по номеру, имени, телефону или нику меньше чем за 10 секунд.
- У каждой заявки есть статус. На главной видно, сколько новых заявок ждут ответа дольше 24 часов: сайт обещает ответ «в течение рабочего дня».
- У каждого изменения (статус, публикация, рассылка, удаление, роль) в журнале записаны автор и время.
- Сайт откатывается на любую прежнюю публикацию в два нажатия.
- Всё, что сейчас умеют команды бота, `/council` и встроенная админка, есть в панели (п. 3.2).

## 2. Термины

| Термин | Значение |
| --- | --- |
| Панель | веб-админка `/admin`, о которой это ТЗ |
| Заявка | запись в `orders` (`data/orders.sqlite3`): с сайта студии или из конструктора ТЗ в боте (`/brief`) |
| Лид | заявка с сайта клиента студии, таблица `leads` в `data/studio.sqlite3` |
| Проект | сайт, который собирает студия агентов, таблица `projects` |
| Урок | запись памяти агентов, таблица `lessons` |
| Контент сайта | JSON в блоке `<script type="application/json" id="site-data">` страницы `site/index.html` |
| Сотрудник | пользователь панели с личным логином и ролью |
| Повторное подтверждение | свежий (не старше 10 минут) ввод кода из Telegram или пароля перед опасным действием |

## 3. Границы работ

### 3.1 Что входит

Вход и сотрудники, главная, заявки, контент сайта, рассылки и подписчики, студия (проекты, совет, уроки, агенты, лиды), журнал действий, системный раздел.

Структура навигации:

```
Codex Lab · Панель
├── Главная
├── Заявки          список · карточка заявки
├── Сайт            Контакты · Бренд и тексты · Цены · Примеры · Вопросы · Публикация и история
├── Рассылки        Новая · История · Подписчики
├── Студия          Проекты · Совет · Уроки · Агенты · Лиды
├── Журнал
├── Система
└── Сотрудники      (только Владелец)
```

### 3.2 Куда переезжают существующие функции

| Сейчас | В панели |
| --- | --- |
| `/last` | Заявки → список |
| `/stats` | Главная → воронка |
| `/forget 12` | Заявка → «Удалить по просьбе клиента» |
| `/post` | Рассылки → Новая |
| `/subscribers` | Рассылки → Подписчики |
| `/studio` | Студия → Проекты |
| `/lessons` с кнопками «Одобрить» / «Удалить» | Студия → Уроки → «На проверке» |
| `/council` | Студия → Совет |
| `POST /api/studio/projects`, `…/revise`, `…/rate` | Студия → проект → кнопки |
| Встроенная админка, 6 вкладок | Сайт → те же 6 вкладок |
| Копирование из `site/backups/` по SSH | Сайт → Публикация и история |

Команды бота остаются: панель их дополняет, а не заменяет.

### 3.3 Что не входит

- Счета, оплата, договоры и полноценная CRM. От воронки продаж в панели будут только статус заявки и сумма договора.
- Правка `.env` и секретов (`BOT_TOKEN`, `ANTHROPIC_API_KEY`) из браузера.
- Личный кабинет клиента студии: клиенты, как и раньше, работают через бот и страницу `/studio/p/<токен>`.
- Визуальный редактор сайтов клиентов. Агенты, как и раньше, отдают только данные, а HTML пишет рендерер.
- Несколько студий в одной панели.
- Интерфейс панели на узбекском и английском. Сама панель только на русском, но контент сайта, как и сейчас, правится на трёх языках.

Правила:

- Права проверяет сервер на каждом запросе, по умолчанию всё запрещено. Скрытая в интерфейсе кнопка защитой не считается.

## 5. Функциональные требования

### 5.1 Вход и сотрудники (AUTH)

- **AUTH-1. Вход в два шага:** логин и пароль, затем шестизначный код, который бот присылает в личный Telegram сотрудника. Код действует 5 минут; после 5 неверных попыток он сгорает.
- **AUTH-2. Без бота.** Если `BOT_TOKEN` не задан, код отправить некуда, поэтому вход идёт только по паролю. На главной у владельца в этом случае постоянно висит предупреждение.
- **AUTH-3. Первый запуск.** Пока в панели нет ни одного сотрудника, `ADMIN_PASSWORD` открывает только мастер «Создать владельца»: имя, логин, пароль не короче 12 символов (как сейчас для `ADMIN_PASSWORD`) и привязка Telegram. После создания владельца `ADMIN_PASSWORD` в панель больше не пускает.
- **AUTH-4. Привязка Telegram** — по ссылке `https://t.me/<бот>?start=link-<одноразовый токен>`, которая действует 15 минут. Бот обрабатывает этот `/start` раньше подписки на новости и отвечает: «Чат привязан к панели: Имя».
- **AUTH-5. Защита от перебора.** После 5 неудачных входов за 15 минут вход приостанавливается на 15 минут, отдельно для адреса и для логина. Используется существующий `RateLimiter`, IPv6 считается по сети /64, как в `_rate_key`.
- **AUTH-6. Сессии.** Сессия завершается через 2 часа бездействия и не живёт дольше 12 часов. В профиле есть список своих сессий (устройство, время), кнопки «Выйти» и «Выйти на всех устройствах».
- **AUTH-7. Сотрудники** (только владелец). Пригласить: имя, логин, роль → ссылка-приглашение на 48 часов, по которой сотрудник задаёт пароль и привязывает Telegram. Можно сменить роль, отключить (все сессии гаснут сразу) и включить обратно. Сотрудники не удаляются: иначе журнал потеряет авторов.
- **AUTH-8. Профиль:** смена своего пароля (нужен старый) и перепривязка Telegram.
- **AUTH-9. Восстановление доступа.** Владелец выдаёт сотруднику новую ссылку для смены пароля. Если владелец сам потерял доступ, на сервере выполняется `venv/bin/python -m app.admin reset-owner <логин>`: команда печатает одноразовую ссылку на 30 минут.
- **AUTH-10 (v2).** У сотрудника появляется флажок «Присылать заявки в Telegram», который со временем заменит `ADMIN_CHAT_IDS`. До тех пор список из `.env` работает как сейчас.

### 5.2 Главная (DASH)

- **DASH-1. Заявки:** новых сегодня и за 7 дней; «Новая» дольше 24 часов (красным, по клику открывается отфильтрованный список); в работе; договоров за месяц и их сумма.
- **DASH-2. Воронка за 7 и 30 дней:** открыли сайт → начали ТЗ → собрали ТЗ → отправили заявку. Рядом конверсии и цели 5 % и 50 %, как в `/stats`, и график по дням за 30 дней. Данные из таблицы `events`: она хранит только счётчики, без адресов и устройств.
- **DASH-3. Студия:** проектов в очереди, в сборке и с ошибкой; расход Claude за текущий месяц (сумма `cost_usd`); средняя оценка клиентов; число уроков на проверке.
- **DASH-4. Рассылки:** активных подписчиков; итог последнего выпуска — доставлено, ошибок, идёт ли рассылка.
- **DASH-5. Предупреждения:** есть недоставленные заявки или лиды; курс NBU недоступен и цены в долларах считаются по запасному курсу; не задан бот, `PUBLIC_URL` или `ADMIN_PASSWORD`; студия в офлайн-режиме.
- **DASH-6.** Редактор и Наблюдатель видят главную без имён и контактов.

### 5.3 Заявки (ORD)

Статусы:

| Код | Название | Когда ставится |
| --- | --- | --- |
| `new` | Новая | автоматически, когда заявка пришла |
| `in_work` | В работе | менеджер связался с клиентом |
| `proposal` | КП отправлено | клиенту отправлено предложение |
| `won` | Договор | договор подписан; указывается сумма |
| `lost` | Отказ | клиент отказался; причина обязательна: дорого, сроки, выбрал другого, не отвечает, другое (своим текстом) |
| `spam` | Спам | мусор; в конверсиях не участвует |

Переходы свободные: статус можно сменить на любой, и каждая смена пишется в ленту заявки и в журнал.

- **ORD-1. Список:** №, дата и время по Ташкенту, источник (сайт или бот), тип проекта, имя, контакт, ориентир цены, статус, ответственный. По 50 на страницу, новые сверху.
- **ORD-2. Поиск и фильтры.** Над списком вкладки статусов со счётчиками. Фильтры: статус, источник, тип проекта, период, ответственный, «не доставлена в Telegram». Поиск идёт по номеру, имени, нику Telegram и по цифрам телефона без учёта формата: «901234567» находит «+998 (90) 123-45-67». Фильтры сохраняются в адресе страницы, поэтому ссылкой можно поделиться.
- **ORD-3. Карточка заявки:**
  - шапка: №, статус, ответственный, источник, дата;
  - контакты с действиями «Позвонить» (`tel:`), «Написать» (`t.me/ник`) и «Скопировать»;
  - проект и ориентир цены;
  - ТЗ целиком в том виде, в каком оно пришло, с кнопками «Скопировать» и «Скачать .txt»;
  - ответы клиента из `brief_json` таблицей «вопрос — ответ»;
  - доставка в Telegram: доставлена или нет, сколько было попыток.
- **ORD-4. Лента заявки:** заметки сотрудников и системные события (статус, ответственный, сумма) с автором и временем. Клиент ленту не видит.
- **ORD-5. Действия:** сменить статус; назначить ответственного (из владельцев и менеджеров); указать сумму договора в сумах (при статусе «Договор») или причину отказа (при «Отказ»); «Отправить в Telegram ещё раз» (сбрасывает `attempts` и будит `Notifier`); массово сменить статус или ответственного у выбранных заявок.
- **ORD-6. Удаление по просьбе клиента.** Заявка удаляется вместе с заметками и контактами безвозвратно, как при `/forget`. Нужно повторное подтверждение и ввод номера заявки. В журнале остаётся запись «Заявка № 12 удалена по просьбе клиента» без имени и телефона. Счётчики воронки не меняются: в них нет персональных данных.
- **ORD-7. Выгрузка CSV** по текущему фильтру: UTF-8 с BOM, чтобы Excel не ломал кириллицу, разделитель `;`. Текст ТЗ включается только отдельной галочкой. Ячейки, которые начинаются с `=`, `+`, `-` или `@`, экранируются апострофом, чтобы Excel не выполнил формулу. Каждая выгрузка пишется в журнал.
- **ORD-8.** Если задан `PUBLIC_URL`, в сообщении бота о новой заявке появляется кнопка «Открыть в панели» со ссылкой `PUBLIC_URL/admin/orders/<номер>`.
- **ORD-9.** Список и карточка обновляются без перезагрузки: раз в 30 секунд новые заявки подтягиваются и подсвечиваются.
- **ORD-10 (v2).** Уведомление браузера о новой заявке; кнопки «В работу» и «Спам» прямо в сообщении бота.

### 5.4 Контент сайта (SITE)

- **SITE-1. Те же шесть вкладок и поля,** что во встроенной админке: «Заявки и контакты»; «Бренд и тексты» (RU/UZ/EN, SEO); «Цены» (типы проектов, надбавки за функции, модификаторы, подпись валюты, запасной курс доллара); «Примеры» (до 12 проектов с обложками, демо-концепты); «Вопросы» (до 20 на каждом языке); «Публикация». Ограничения длины и проверки — те же, что в коде сайта (`pairError`, `safeUrl`, `safeCover` и др.). Сервер повторяет каждую проверку сам и не полагается на браузер.
- **SITE-2. Черновик на сервере.** Он переживает закрытие вкладки и смену устройства. Черновик один на всех, у него есть номер ревизии. Если черновик успели изменить, сохранение возвращает конфликт: «Черновик изменил Имя в 14:05 — загрузить его версию или перезаписать?». Молча правки не теряются.
- **SITE-3. Предпросмотр** — страница `/admin/preview`: сайт с данными черновика, доступный только вошедшим. На ней плашка «Предпросмотр, не опубликовано» и заголовок `X-Robots-Tag: noindex`.
- **SITE-4. Публикация на стороне сервера.** Сервер берёт текущий `site/index.html` и заменяет содержимое блока `site-data` проверенным JSON, экранируя `<` как `<`, чтобы текст не закрыл тег `<script>`. Запись идёт через существующую `_write_site`: копия в `site/backups/`, затем атомарная подмена файла. Браузер больше не отправляет страницу целиком. Бот подхватывает новые цены сам (`SitePricing` перечитывает файл, когда меняется время изменения) — это нужно закрепить тестом.
- **SITE-5. История публикаций:** дата, автор, комментарий и список изменённых полей. Любую версию можно сравнить с текущей и вернуть кнопкой «Вернуть эту версию». Возврат создаёт новую публикацию, старые не удаляются. JSON версий хранится в базе панели без ограничения числа; файловые копии в `site/backups/` — как сейчас, последние 20.
- **SITE-6.** Как и сейчас, можно выгрузить и загрузить настройки файлом JSON и скачать сайт одним файлом.
- **SITE-7.** «Сбросить все настройки» меняет только черновик; на сайт сброс попадает после публикации.
- **SITE-8. Обложки проектов.** Обрезка до 4:3 и сжатие в JPEG остаются в браузере, как сейчас, — без новых зависимостей на сервере. Сервер принимает только `data:image/(jpeg|png|webp);base64` короче 700 000 символов (то же правило, что в `safeCover`).
- **SITE-9. Встроенная админка.** Когда сайт открыт с сервера, кнопки «Вход для владельца» и «Админка» ведут в `/admin/site`. Когда сайт открыт как файл или внутри Claude, встроенная админка остаётся как есть, в режиме «скачать файл».

### 5.5 Рассылки и подписчики (NEWS)

- **NEWS-1. Новый выпуск:** заголовок до 120 знаков, текст до 3500 знаков (с фото — до 1000, это предел подписи в Telegram), ссылка (превращается в кнопку «Подробнее»), фото JPG/PNG до 10 МБ. У полей счётчики символов.
- **NEWS-2. Предпросмотр «как в Telegram»** (формат `news_text`: «📰 Заголовок», пустая строка, текст) и кнопка «Отправить тест себе» — в привязанный чат автора. Выпуск с фото без теста не уходит: при тестовой отправке Telegram возвращает `file_id`, и вся рассылка идёт по нему, как сейчас при `/post` с фото.
- **NEWS-3. Отправка** с подтверждением «Отправить выпуск 1 284 подписчикам?». Рассылкой занимается существующий `Broadcaster` с таблицей `news_deliveries`, поэтому дублей не бывает.
- **NEWS-4. Ход рассылки:** отправлено, ошибок, осталось; обновляется раз в 5 секунд. Рассылка идёт и при закрытой панели, и после перезапуска сервера — как сейчас.
- **NEWS-5. История:** дата, автор, заголовок, доставлено и ошибок, статус. Любой выпуск можно открыть и сделать из него копию.
- **NEWS-6. Подписчики:** активных, всего, отписавшихся; график прироста по дням. Список с поиском (имя в Telegram, дата подписки, статус) видят только владелец и менеджер. `chat_id` в интерфейсе не показывается.
- **NEWS-7 (v2).** Черновики выпусков и отправка по расписанию (время по Ташкенту).
- **NEWS-8 (v2).** Рассылка по языку подписчика. Сначала язык нужно начать хранить в базе: сейчас `ChatPrefs` держит его только в памяти.

- **STU-1. Проекты:** №, название, ниша, стиль, статус («В очереди» `queued`, «Собирается» `running`, «Готов» `done`, «Ошибка» `failed`), версия, оценка ревью из 10, оценка клиента в звёздах, вызовы Claude, стоимость в $, откуда заказан (бот или панель), дата. Фильтры по статусу и периоду, поиск по названию и адресу.
- **STU-2. Карточка проекта:** поля брифа; ссылки на сайт и все версии `/sites/<slug>/vN`; ссылка на страницу клиента `/studio/p/<токен>` с кнопкой «Скопировать»; ожидающие правки; текст ошибки; стоимость. Внутри вкладки «Совет» (лента реплик по каналам, как на `/council`), «Задачи», «Уроки проекта», «Лиды».

- **STU-4. Действия:** «Отправить правки» (до 1500 знаков); «Оценить» (1–5); «Перезапустить» для проекта с ошибкой (статус снова `queued`, воркер просыпается); «Удалить проект» — только владелец, с повторным подтверждением: удаляются проект, его лента, задачи, лиды и файлы сайта.
- **STU-5 (v2).** «Снять сайт с публикации»: адрес отвечает 410, файлы сохраняются, сайт можно вернуть.
- **STU-6. Совет:** общая лента всех проектов с фильтром по каналу, агенту и проекту — замена `/council`. Публичная страница `/studio/p/<токен>` не меняется.
- **STU-7. Уроки.** Вкладки «На проверке» (кнопки «Одобрить» и «Удалить», как в `/lessons`), «Действующие», «Отключённые»; фильтр по агенту. У каждого урока видны агент, текст, вес, сколько раз применялся и из какого проекта. Урок можно переписать, отключить или включить; новый урок, добавленный вручную, действует сразу — как уроки из веб-панели по README.
- **STU-8. Агенты:** таблица из 20 агентов — уровень, уроков, реплик, проектов, средняя оценка клиентов.
- **STU-9. Лиды:** заявки со всех сайтов клиентов — дата, сайт, имя, телефон, сообщение, доставлен ли лид владельцу сайта. Действия: «Доставить ещё раз» и «Удалить по просьбе». Это данные покупателей наших клиентов, поэтому доступ только у владельца и менеджера.
- **STU-10 (v2).** Лимиты студии (`STUDIO_DAILY_LIMIT`, `STUDIO_MAX_CALLS`, пауза очереди) меняются в панели без перезапуска.

### 5.7 Журнал действий (LOG)

- **LOG-1. Что пишется:** входы (успешные и нет), выходы; изменения заявок, удаления и выгрузки; публикации и откаты сайта; рассылки; действия с проектами, уроками и лидами; изменения сотрудников и ролей; резервные копии. Действия админов в боте (`/forget`, `/post`, проверка уроков) тоже пишутся — с автором «бот, чат …».
- **LOG-2. Запись:** время, сотрудник, действие, объект (тип и номер), подробности «было → стало», ключ адреса (для IPv6 — сеть /64).
- **LOG-3.** Персональных данных клиентов в журнале нет: только номера объектов и названия полей.
- **LOG-4.** Из панели журнал нельзя ни править, ни удалить. Записи хранятся 365 дней, потом удаляются автоматически.
- **LOG-5. Фильтры:** сотрудник, тип действия, объект, период.

### 5.8 Система (SYS)

- **SYS-1. Состояние:** бот (подключён ли, ник), Claude (включён, модель) или офлайн-режим, публикация, `PUBLIC_URL`, сколько чатов в `ADMIN_CHAT_IDS`, версия программы (коммит), размер папки `data/`, свободное место на диске. Секреты никогда не показываются — только «задан» или «не задан».
- **SYS-2. Очереди:** недоставленные заявки и лиды, текущая рассылка, очередь студии. У каждой кнопка «Повторить сейчас», которая будит нужный цикл.
- **SYS-3. Курс доллара:** текущий курс, дата и источник (`nbu`, `cbu` или запасной из настроек сайта), кнопка «Обновить сейчас».
- **SYS-4. Резервная копия** (только владелец, с повторным подтверждением): архив .zip. Базы снимаются через SQLite backup API, чтобы не скопировать базу посреди записи. Два варианта: «базы, курс и сайт студии» или «всё, включая сайты клиентов». Каждая копия пишется в журнал.

## 6. Нефункциональные требования

### 6.1 Архитектура

- Панель работает в том же процессе aiohttp, в новом пакете `app/admin/`. Отдельного сервиса, Node.js и сборки нет: как и `council.html`, это статические файлы `app/admin/assets/` (один HTML, один JS, один CSS) и JSON-API `/api/admin/*`.
- Все адреса `/admin` и `/admin/*`, кроме `/admin/preview`, отдают один `admin.html`, а навигация идёт через History API. Ссылки вида `/admin/orders/12` открываются напрямую.
- Новые зависимости не добавляются: пароли — `hashlib.scrypt`, токены — `secrets`, базы — `sqlite3`, графики — встроенный SVG. Если без зависимости не обойтись, её отдельно согласуют с владельцем.
- Новая база — `data/admin.sqlite3`: сотрудники, сессии, коды, журнал, версии контента. Существующие базы меняются только добавлением столбцов и таблиц (раздел 7).
- Ошибка в панели не должна ломать сайт, приём заявок, бот и студию. Обработчик панели, упавший с исключением, отвечает 500 с номером запроса, а в журнал сервера пишет трассировку без персональных данных.
- Ответы API — в формате существующего: `{"ok": true, …}` или `{"ok": false, "error": "текст для человека"}`. Коды: 400, 401 (нет сессии), 403 (нет прав или чужой Origin), 404, 409 (конфликт черновика), 413, 429.

### 6.2 Безопасность

- **Cookie сессии:** `__Host-cl_admin`, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`. Токен — 256 бит (`secrets.token_urlsafe(32)`), в базе хранится только его SHA-256.
- **CSRF.** Изменяющий запрос принимается, только если выполнены все три условия: `SameSite=Strict`, заголовок `Origin` совпадает с адресом сервера (`PUBLIC_URL` или `Host`), тело в `application/json`.
- **Пароли:** scrypt (n = 2¹⁴, r = 8, p = 1, соль 16 байт), не короче 12 символов и не совпадают с логином. Сравнение — `hmac.compare_digest`.
- **Одноразовые коды:** 6 цифр из `secrets.randbelow`, в базе хранится хеш, срок и число попыток ограничены (AUTH-1).
- **Проверка прав** собрана в одном месте — декоратор с перечнем ролей. Маршрут без декоратора не регистрируется (проверяется тестом).
- **XSS.** Тексты заявок и лидов приходят из интернета, в том числе от злоумышленников. Выводятся они только через `textContent` или экранирование. CSP панели без `unsafe-inline`:
  `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`.
  У `/admin/preview` — CSP самого сайта, как у `/`.
- **Заголовки** у всех ответов `/admin*` и `/api/admin/*`: `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`.
- **Только известные поля:** API берёт из запроса заранее перечисленные поля, как `brief_from`, остальные игнорирует. Роль, автор и время берутся из сессии, а не из тела запроса.
- **Журнал сервера** (`journalctl`): никаких имён, телефонов, текстов заявок, паролей, кодов и токенов. Это действующее правило проекта, оно распространяется и на панель.
- **(v2)** Личные API-токены с правами вместо общего `ADMIN_PASSWORD` в Bearer API.

### 6.3 Персональные данные

- В панели хранятся и показываются имена, телефоны и ники клиентов студии и их покупателей (лиды). Доступ есть только у ролей из раздела 4; каждое удаление и каждая выгрузка пишется в журнал.
- Удаление по просьбе клиента безвозвратно для живых баз. В README нужно описать, что делать с резервными копиями, сделанными до удаления.
- До запуска юрист проверяет требования закона РУз «О персональных данных», в том числе о хранении данных граждан Узбекистана на серверах в Узбекистане (открытый вопрос 6).

### 6.4 Производительность

- Расчётный объём — 50 000 заявок, 100 000 подписчиков и 5 000 проектов на самом дешёвом VPS из README.
- Список и карточка отвечают за 300 мс (p95); панель открывается за 2 с на 4G; HTML, JS и CSS панели вместе весят не больше 150 КБ без сжатия.
- Списки постраничные, по 50 строк, с keyset-пагинацией по номеру (`WHERE number < ?`), а не `OFFSET`.
- Запросы идут через существующий `SQLiteStore._run` — один поток и блокировка на базу. Долгие операции (выгрузка, архив) работают порциями по 1000 строк и отпускают блокировку между ними, чтобы приём заявок не ждал дольше секунды.

### 6.5 Интерфейс

- Язык — русский. Время показывается по Ташкенту (UTC+5), хранится в UTC, как сейчас. Даты — `04.11.2026 14:05`, суммы — «7,5 млн сум», «1 250 000 сум».
- С ширины 360 px без горизонтальной прокрутки работают как минимум список и карточка заявки (статус, заметка), главная и рассылка. Остальное допустимо в упрощённом виде.
- Светлая и тёмная тема — по настройке системы. Внешний вид строится на токенах сайта Codex Lab (цвета, шрифты, скругления).
- Доступность: всё работает с клавиатуры, фокус виден, контраст текста не ниже 4,5:1, у полей есть подписи, ошибка показывается рядом с полем.
- Пустые состояния и ошибки объясняются простым языком и подсказывают, что сделать, — в том же тоне, что README.
- Браузеры: две последние версии Chrome, Edge, Firefox и Safari; iOS 16+, Android 10+.

### 6.6 Надёжность и сопровождение

- Миграции запускаются сами при старте, их можно повторять, и они только добавляют (столбцы не удаляются). Перед первой миграцией сервер копирует каждую базу в `*.sqlite3.bak-<дата>`.
- Тесты пишутся в `tests/` на `unittest`, как сейчас: Telegram и Claude подменены заглушками. Обязательный набор: вход и код, срок сессии, матрица прав (каждый маршрут × каждая роль × без сессии), CSRF, перебор паролей, миграции на копии старой базы, проверка контента и сборка `index.html`, удаление по просьбе, экранирование CSV, XSS в данных заявки.
- В README появляется раздел «Админ-панель»: первый вход, приглашение сотрудников, восстановление доступа, резервная копия.

### 7.1 Новая база `data/admin.sqlite3`

```sql
CREATE TABLE users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    login         TEXT NOT NULL UNIQUE COLLATE NOCASE,
    name          TEXT NOT NULL,
    role          TEXT NOT NULL CHECK (role IN ('owner', 'manager', 'editor', 'viewer')),
    pass_hash     TEXT NOT NULL DEFAULT '',             -- scrypt$n$r$p$соль$хеш; пусто — приглашение не принято
    tg_chat_id    INTEGER UNIQUE,                       -- личный чат для кодов; NULL — не привязан
    active        INTEGER NOT NULL DEFAULT 1 CHECK (active IN (0, 1)),
    created_at    TEXT NOT NULL,
    last_login_at TEXT NOT NULL DEFAULT ''
);
CREATE TABLE sessions (
    token_hash  TEXT PRIMARY KEY,                       -- SHA-256 от токена из cookie
    user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at  TEXT NOT NULL,
    seen_at     TEXT NOT NULL,
    expires_at  TEXT NOT NULL,                          -- created_at + 12 ч
    stepup_at   TEXT NOT NULL DEFAULT '',               -- последнее повторное подтверждение
    ip_key      TEXT NOT NULL,
    user_agent  TEXT NOT NULL DEFAULT ''
);
CREATE INDEX sessions_user ON sessions (user_id);
CREATE TABLE one_time_codes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    purpose     TEXT NOT NULL CHECK (purpose IN ('login', 'stepup', 'invite', 'link_tg', 'reset')),
    code_hash   TEXT NOT NULL,
    attempts    INTEGER NOT NULL DEFAULT 0,
    expires_at  TEXT NOT NULL,
    used_at     TEXT NOT NULL DEFAULT ''
);
CREATE INDEX one_time_codes_user ON one_time_codes (user_id, purpose);
CREATE TABLE audit (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    at          TEXT NOT NULL,
    user_id     INTEGER REFERENCES users(id),           -- NULL — система или бот
    actor       TEXT NOT NULL DEFAULT '',               -- «бот, чат 123» для действий из Telegram
    action      TEXT NOT NULL,                          -- order.status, order.forget, site.publish, news.send…
    object_type TEXT NOT NULL DEFAULT '',
    object_id   TEXT NOT NULL DEFAULT '',
    details     TEXT NOT NULL DEFAULT '{}',             -- было → стало, без персональных данных
    ip_key      TEXT NOT NULL DEFAULT ''
);
CREATE INDEX audit_at ON audit (at);
CREATE INDEX audit_user ON audit (user_id, at);
CREATE TABLE site_versions (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at    TEXT NOT NULL,
    user_id       INTEGER REFERENCES users(id),
    comment       TEXT NOT NULL DEFAULT '',
    data_json     TEXT NOT NULL,                        -- содержимое site-data
    restored_from INTEGER REFERENCES site_versions(id)  -- если это откат
);
CREATE TABLE site_draft (
    id           INTEGER PRIMARY KEY CHECK (id = 1),    -- черновик один на всех
    data_json    TEXT NOT NULL,
    base_version INTEGER REFERENCES site_versions(id),  -- от какой публикации начат
    revision     INTEGER NOT NULL DEFAULT 0,            -- растёт при каждом сохранении: защита от затирания
    updated_at   TEXT NOT NULL,
    user_id      INTEGER REFERENCES users(id)
);
```

При первом запуске в `site_versions` записывается текущий контент из `site/index.html` как версия № 1 («исходная»).

## 8. API панели

Все маршруты, кроме входа, требуют сессию. Роли указаны по разделу 4; «+п» — нужно повторное подтверждение.

| Метод и путь | Роли | Что делает |
| --- | --- | --- |
| `POST /api/admin/login` | — | логин и пароль → отправка кода в Telegram (или сессия сразу, если бота нет) |
| `POST /api/admin/login/code` | — | код → cookie сессии |
| `POST /api/admin/logout` | все | выйти |
| `GET /api/admin/me` | все | кто я, роль, список прав для интерфейса |

## 9. Совместимость и переход

- **Команды бота** не меняются. Изменения, сделанные через бот, видны в панели и пишутся в журнал.
- **`/api/publish`** (загрузка страницы целиком) работает до конца этапа 2. Потом встроенная админка на сервере ведёт в панель, а маршрут отвечает 410.
- **`/council`** с паролем работает до конца этапа 3, потом перенаправляет на `/admin/studio/council`. Страница клиента `/studio/p/<токен>` не меняется.
- **Служебное Bearer API** с `ADMIN_PASSWORD` работает, как описано в README. В v2 его заменят личные API-токены, после чего пароль для API можно будет выключить.
- **`ADMIN_PASSWORD`** после создания первого владельца больше не пускает в панель, но пока нужен для Bearer API и `/council`.
- **Старые заявки** при миграции получают статус «Новая», а источник определяется по пометке «из Telegram-бота». Чтобы старые заявки не выглядели просроченными, при первом входе панель предлагает владельцу разобрать их массовым действием.
- **Обновление сервера** — как сейчас: скопировать файлы, `sudo systemctl restart codexlab`. Ничего нового в `.env` для старта не требуется.

## 11. Критерии приёмки

1. **Первый вход.** На чистой установке вход по `ADMIN_PASSWORD` открывает только мастер владельца. После создания владельца `ADMIN_PASSWORD` в панель не пускает.
2. **Вход и перебор.** Вход работает с кодом из Telegram. Пять неверных кодов — код сгорает; пять неверных паролей за 15 минут — вход закрыт на 15 минут.
3. **Отключение.** Отключённый сотрудник теряет доступ на следующем же запросе, даже с открытой вкладкой.
4. **Права.** Автотест обходит каждый маршрут `/api/admin/*` под каждой ролью и без сессии. Результат совпадает с разделом 4, а маршрутов без проверки прав нет.
5. **CSRF.** Изменяющий запрос с чужим `Origin` получает 403.
6. **Новые заявки.** Заявки с сайта и из бота появляются в списке не позже чем через 30 секунд, с правильным источником. У уведомления в Telegram есть кнопка «Открыть в панели».
7. **Поиск по телефону.** Запрос «901234567» находит заявку с телефоном «+998 (90) 123-45-67».
8. **Смена статуса** видна в ленте заявки и в журнале, с автором и временем.
9. **Удаление по просьбе.** После удаления заявки и её заметок нет в базе, `/last` её не показывает, а в журнале нет имени и телефона.
10. **CSV** открывается в Excel с нормальной кириллицей. Имя клиента `=1+1` выводится как текст.
11. **XSS.** Заявка с `<img src=x onerror=alert(1)>` в имени и в ТЗ показывается как текст: скрипт не выполняется ни в списке, ни в карточке, ни в выгрузке.
12. **Публикация.** Публикация из панели меняет сайт, и `/prices` в боте сразу считает по новым ценам без перезапуска. Откат возвращает прежний сайт и прежние цены.
13. **Два редактора.** Когда двое правят черновик одновременно, второй получает предупреждение о конфликте. Ничьи правки молча не теряются.
14. **Рассылка.** Тест приходит только автору. Если перезапустить сервер посреди рассылки, никто не получит выпуск дважды.
15. **Уроки.** Урок, одобренный в панели, начинает применяться агентами (его возвращает `lessons_for`); отключённый урок не применяется.
16. **Ничего не сломано.** Все старые тесты (`venv/bin/python -m unittest discover -s tests -v`) проходят, команды бота работают как раньше.
17. **Телефон.** На экране шириной 360 px менеджер открывает заявку, меняет статус и пишет заметку без горизонтальной прокрутки.
18. **Журнал сервера.** После прогона всех сценариев в `journalctl -u codexlab` нет имён, телефонов, паролей, кодов и токенов.

## 12. Открытые вопросы к владельцу

1. **Статусы.** Подходят ли статусы заявки и причины отказа из п. 5.3?
2. **Наблюдатель.** Нужна ли роль Наблюдателя уже в первой версии, или хватит трёх ролей?
3. **Редактор.** Публикует ли редактор сайт сам или только готовит черновик, а публикует менеджер?
4. **Код из Telegram.** Нужен ли он всем ролям или только владельцу и менеджеру?
5. **Команда.** Сколько сотрудников будет в панели в ближайшие полгода? От этого зависит, нужны ли назначение ответственных и фильтр по ним уже в первом этапе.
6. **Персональные данные.** Где физически стоит сервер? Нужна ли автоматическая очистка заявок «Отказ» и «Спам» старше N месяцев, и если да, какое N?
7. **Сумма договора.** Нужны ли сумма и отчёт «договоров за месяц» уже на первом этапе?
8. **Адрес панели.** `/admin` на основном домене или отдельный поддомен, например `admin.codexlab.uz`? Поддомен — это отдельный сертификат в Caddy и отдельные cookie.
9. **Язык панели.** Нужен ли интерфейс на узбекском, и когда?
