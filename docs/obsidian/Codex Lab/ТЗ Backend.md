# ТЗ для backend-разработчика

> [!info] Контекст
> Сервер — один процесс на Python 3.11+ (aiohttp 3.14 + aiogram 3.31 + anthropic 1.11), три базы SQLite, systemd и Caddy.
> Обзор кода — в [[00 Обзор проекта]], найденные проблемы — в [[01 Аудит сайта]].
> Требования к безопасности задаёт [[ТЗ Кибербезопасность]], план событий — [[ТЗ Data Engineer]].

## Правила

- **Стек не меняем без причины.** Python + aiohttp + aiogram + SQLite остаются. На PostgreSQL переходим, только если понадобится больше одного процесса сервера; тогда — отдельная задача.
- Каждая задача — отдельный PR с тестами. Сейчас 63 теста, все проходят; число может только расти.
- Telegram и Claude в тестах подменены заглушками — так и оставить: тесты не шлют сообщения и не тратят деньги.
- Имена, телефоны и тексты ТЗ в журнал не пишем (как сейчас).
- Новые настройки — в `.env.example` с комментарием на русском, проверка значений — в `app/config.py`.
- Всё, что «уже сделано хорошо», перечислено в конце [[01 Аудит сайта]]. Это не ломать.

## P0

### BE-01 · Контент сайта и цены — один источник

**Зачем.** Сейчас весь контент живёт внутри `site/index.html` в блоке `<script id="site-data">`. Админка пересобирает весь HTML и шлёт его на `POST /api/publish`. Бот достаёт цены из HTML регулярным выражением (`app/brief_bot.py:35`, `read_pricing` на строке 294), а при сбое молча берёт `DEFAULT_PRICING` (строка 38). Справочники `TYPES` и `FEATURES` продублированы в Python и JS.

**Что сделать.**
1. Хранить контент в `data/site.json` (бренд, контакты, тексты на 3 языках, цены, проекты, FAQ, демо). Описать JSON Schema и проверять ею каждую запись.
2. Справочники (типы проектов, функции, модификаторы, цели) вынести в `app/catalog.json`, общий для бота и сайта. Удалить дубли из `app/brief_bot.py`.
3. Картинки проектов — файлами в `data/uploads/` (см. BE-11, загрузка), а не base64 внутри страницы.
4. API:

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| GET | `/api/site` | все | опубликованный контент (ETag, `Cache-Control: max-age=60`) |
| GET | `/api/admin/site/draft` | editor+ | черновик |
| PUT | `/api/admin/site/draft` | editor+ | сохранить черновик (проверка схемы, лимит 256 КБ) |
| POST | `/api/admin/site/publish` | owner | черновик → опубликован, прежняя версия → история |
| GET | `/api/admin/site/versions` | editor+ | список версий: кто, когда, что поменял |
| POST | `/api/admin/site/rollback/{version}` | owner | откат |
| POST | `/api/admin/uploads` | editor+ | загрузка картинки (см. требования в [[ТЗ Кибербезопасность]] SEC-08) |

5. Страницы рендерятся на сервере из `site.json` по шаблонам фронтенда (договориться с [[ТЗ Frontend]] FE-02). `/api/publish` с целым HTML — удалить после переезда.
6. Скрипт миграции: достать `site-data` из текущего `index.html` и записать `site.json`; картинки base64 — в файлы.

**Готово, когда:**
- [ ] Бот и сайт считают цену из одного файла; тест: поменяли цену через API → бот считает по новой без перезапуска.
- [ ] В коде нет `SITE_DATA`-регулярки и `DEFAULT_PRICING`.
- [ ] Неверный JSON отклоняется с понятной ошибкой на русском и указанием поля.
- [ ] Хранятся минимум 50 версий; откат работает.
- [ ] Миграция текущего сайта проходит без потерь (сравнение до и после в тесте).

### BE-02 · Учётные записи, сессии, роли, 2FA

**Зачем.** Один `ADMIN_PASSWORD` открывает всё: публикацию, рассылку всем подписчикам, API студии, совет агентов. Пароль ходит в каждом запросе в `Authorization: Bearer`, а страница совета хранит его в `sessionStorage` (`app/studio/assets/council.html:144`). Подробные требования — [[ТЗ Кибербезопасность]] SEC-01.

**Что сделать.**
1. Таблица `users`: логин, хеш пароля (argon2id), секрет TOTP (зашифрован ключом из `.env`), роль, `telegram_user_id`, `disabled`, даты.
2. Роли:

| Роль | Что может |
| --- | --- |
| `owner` | всё, включая пользователей, публикацию и рассылку |
| `editor` | черновики контента, загрузки, просмотр заявок |
| `manager` | заявки (CRM), проекты студии, уроки |
| `viewer` | только просмотр |

3. Вход: `POST /api/auth/login` (логин + пароль) → `POST /api/auth/2fa` (TOTP) → cookie сессии `HttpOnly; Secure; SameSite=Strict; Path=/`, срок 12 ч, продление при активности, принудительный выход через 7 дней.
4. Сессии в базе (`sessions`: id-хеш, user_id, создана, последняя активность, IP-ключ, user-agent). `POST /api/auth/logout`, `GET /api/auth/me`, «выйти со всех устройств».
5. CSRF: для изменяющих запросов — заголовок `X-CSRF-Token` (double-submit) плюс проверка `Origin`.
6. Первый `owner` создаётся командой `python -m app.users create --role owner`. Сброс 2FA — тоже из консоли.
7. Существующий служебный API (`/api/news`, `/api/studio/*`, `/api/council/*`) перевести на сессии; для машин — API-ключи с ролью и сроком (`api_keys`, в базе только хеш).
8. **Бот:** админ определяется по `from_user.id`, а не по `chat.id` (сейчас `app/bot.py:126` и `app/user_bot.py`). Группа в `ADMIN_CHAT_IDS` остаётся только каналом для уведомлений; команды `/post`, `/forget`, `/lessons` принимаются от пользователей, у которых в `users` указан `telegram_user_id`.
9. `ADMIN_PASSWORD` убрать после миграции (оставить переходный период 2 недели с предупреждением в логе).

**Готово, когда:**
- [ ] Без сессии все `/api/admin/*` отвечают 401, с ролью ниже нужной — 403 (тест на каждый маршрут).
- [ ] Пароль и TOTP нигде не хранятся в открытом виде; в `localStorage` и `sessionStorage` ничего секретного.
- [ ] 5 неверных попыток на логин → пауза 15 минут (на логин и на IP), плюс общий лимит на все попытки входа.
- [ ] Участник группы-уведомлений без своей учётки не может выполнить `/post` (тест).

### BE-14 · Потолок расходов на Claude

**Зачем.** Лимит сейчас «2 сайта в сутки на чат» (`STUDIO_DAILY_LIMIT`) и «120 вызовов на проект» (`STUDIO_MAX_CALLS`). Чатов можно завести сколько угодно, поэтому общих расходов ничто не ограничивает.

**Что сделать.**
1. `STUDIO_DAILY_BUDGET_USD` (например, 20) — общий потолок в сутки по Ташкенту. Считать по `projects.cost_usd` и по стоимости текущих проектов.
2. Потолок достигнут → новые проекты встают в очередь до завтра, клиент получает честное сообщение, админ — тревогу.
3. `STUDIO_MAX_QUEUE` — длина очереди; сверх неё бот не принимает заказ.
4. Тревога при 80% бюджета.
5. Новым аккаунтам Telegram (меньше N дней от первого `/start`) — 1 сайт в сутки (настраивается).

**Готово, когда:**
- [ ] Тест: при исчерпанном бюджете проект не уходит в Claude, а ждёт.
- [ ] `/studio` в боте показывает расход за сегодня и остаток.

### BE-06 · База: WAL, миграции, бэкапы

**Что сделать.**
1. `PRAGMA journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL` для всех трёх баз (`app/db.py`).
2. Миграции: таблица `schema_version`, папка `app/migrations/<db>/NNN_*.sql`, применение при старте по порядку в транзакции. Текущую схему оформить миграцией `001`. Ручной `ALTER` из `app/studio/store.py` (`migrate`) — миграцией `002`.
3. Бэкап: systemd-таймер раз в сутки → `VACUUM INTO` каждой базы + архив `data/sites`, `data/uploads`, `site.json` → шифрование (age или gpg, публичный ключ на сервере, приватный — только у владельца) → копия вне сервера (S3-совместимое хранилище или второй VPS). Хранить 7 дневных, 4 недельных, 6 месячных.
4. Скрипт восстановления `deploy/restore.sh` и инструкция в README. Проверка восстановления раз в месяц на staging.
5. Тревога в Telegram, если бэкап не прошёл или старше 26 часов.

**Готово, когда:**
- [ ] Восстановление из бэкапа на чистой машине проходит по инструкции за 30 минут.
- [ ] Бэкапы на сервере и вне его зашифрованы.

**Что сделать.**
1. Своё хранилище FSM для aiogram на SQLite (`BaseStorage`: `set_state`, `get_state`, `set_data`, `get_data`) или Redis, если он появится. Срок жизни незаконченного состояния — 7 дней.
2. `ChatPrefs` — таблица `chat_prefs (chat_id, lang, currency, updated_at)`.
3. После перезапуска бот продолжает с того же шага.

**Готово, когда:**
- [ ] Тест: прошли 3 шага ТЗ, пересоздали диспетчер, продолжили с шага 4 с сохранёнными ответами.

### BE-09 · Приём событий аналитики

Делается по плану событий из [[ТЗ Data Engineer]] (DE-01).

1. `POST /api/event` принимает пачку событий: `[{name, ts, session, props}]`, до 20 за раз, до 4 КБ. Имена и свойства проверяются по списку из плана; неизвестное отбрасывается.
2. Таблица `events_raw` (отдельная база `analytics.sqlite3`): время, `session` (случайный id вкладки, без cookie), имя, свойства JSON. **Без IP, user-agent и контактов.** Класс устройства (`mobile`/`desktop`) присылает фронт.
3. Текущие суточные счётчики `events` оставить, пока DE не переведёт `/stats` на новые таблицы.
4. Бот: метка из deep-link `/start <payload>` сохраняется в `chat_sources (chat_id, first_source, first_seen)`; заявка из бота получает `source` из неё.
5. Ссылки в новостях — через `/r/{news_id}` (счётчик кликов, редирект 302 только на сохранённый URL).
6. Лимит: 60 событий в минуту с IP-ключа (как сейчас — без записи IP).

### BE-11 · Сайты клиентов

Решение по домену — вместе с [[ТЗ Кибербезопасность]] SEC-04.

1. Отдавать сайты клиентов с **отдельного домена** (например, `<slug>.codexlab.site`): изоляция от домена админки. Старые адреса `/sites/<slug>/` → 301 на новый домен.
2. `X-Robots-Tag: noindex` для сайтов, которые не прошли ручное одобрение админом; одобрение — кнопка в `/studio`.
3. Ссылка «Пожаловаться» в подвале сайта клиента → `POST /api/abuse` → тревога админу; админ может снять сайт (`status = blocked`, отдаётся 451).
4. Свой домен клиента (P2): проверка владения через TXT-запись, выпуск сертификата через Caddy on-demand TLS с белым списком доменов из базы.
5. Загрузка логотипа и фото клиентом через бота: только JPEG, PNG, WebP; до 5 МБ; перекодирование и удаление EXIF на сервере; до 10 файлов на проект.
6. Лиды с проектов без `chat_id` (созданных из панели) сейчас никуда не уходят (`app/studio/store.py:412`): отправлять их админам студии или запрещать форму на таких сайтах.

### BE-13 · Сроки хранения и удаление данных

Требования — [[ТЗ Кибербезопасность]] SEC-10.

1. Ежедневная задача очистки:

2. `/forget` расширить: по номеру заявки, по телефону или Telegram — удаляет заявки, лиды, подписку, проекты студии этого чата (с подтверждением).

### BE-10 · Онлайн-оплата

1. Click и Payme (Uzum — по желанию владельца): предоплата по договору из CRM и оплата «ИИ-сайта» (пакеты: публикация на своём домене, N правок, снятие брендинга).
2. Таблица `payments`: внешний id, сумма, статус, подпись провайдера; обработчики колбэков идемпотентны (повтор колбэка не создаёт второй платёж), подпись проверяется.
3. После оплаты: статус заявки или проекта меняется, клиенту и админу — сообщение в Telegram.
4. Тестовый режим провайдеров на staging.
