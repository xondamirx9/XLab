# ТЗ для backend-разработчика

> [!info] Контекст
> Сайты клиентам делают **программисты студии**. Сервер обслуживает продажи: сайт с конструктором ТЗ, Telegram-бот, заявки, новости.
> Один процесс на Python 3.11+ (aiohttp 3.14 + aiogram 3.31), базы SQLite, systemd и Caddy.
> Модуль «ИИ-студия из 20 агентов» не соответствует тому, как работает студия, и удаляется (BE-13).
> Обзор кода — в [[00 Обзор проекта]], найденные проблемы — в [[01 Аудит сайта]].
> Требования к безопасности задаёт [[ТЗ Кибербезопасность]], план событий — [[ТЗ Data Engineer]].

## Правила

- **Стек не меняем без причины.** Python + aiohttp + aiogram + SQLite остаются. На PostgreSQL переходим, только если понадобится больше одного процесса сервера; тогда — отдельная задача.
- Каждая задача — отдельный PR с тестами. Сейчас 63 теста, все проходят; после удаления ИИ-студии часть уйдёт вместе с ней, остальные должны остаться зелёными, новые — добавляться.
- Telegram в тестах подменён заглушкой — так и оставить: тесты не шлют сообщения.
- Имена, телефоны и тексты ТЗ в журнал не пишем (как сейчас).
- Новые настройки — в `.env.example` с комментарием на русском, проверка значений — в `app/config.py`.
- Всё, что «уже сделано хорошо», перечислено в конце [[01 Аудит сайта]]. Это не ломать.

### BE-01 · Контент сайта и цены — один источник

**Зачем.** Сейчас весь контент живёт внутри `site/index.html` в блоке `<script id="site-data">`. Админка пересобирает весь HTML и шлёт его на `POST /api/publish`. Бот достаёт цены из HTML регулярным выражением (`app/brief_bot.py:35`, `read_pricing` на строке 294), а при сбое молча берёт `DEFAULT_PRICING` (строка 38). Справочники `TYPES` и `FEATURES` продублированы в Python и JS.

**Что сделать.**
1. Хранить контент в `data/site.json` (бренд, контакты, тексты на 3 языках, цены, проекты и кейсы, команда, отзывы, условия поддержки, FAQ, демо). Описать JSON Schema и проверять ею каждую запись.
2. Справочники (типы проектов, функции, модификаторы, цели) вынести в `app/catalog.json`, общий для бота и сайта. Удалить дубли из `app/brief_bot.py`.
3. Картинки проектов и фото команды — файлами в `data/uploads/`, а не base64 внутри страницы.
4. API:

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| GET | `/api/site` | все | опубликованный контент (ETag, `Cache-Control: max-age=60`) |
| GET | `/api/admin/site/draft` | editor+ | черновик |
| PUT | `/api/admin/site/draft` | editor+ | сохранить черновик (проверка схемы, лимит 256 КБ) |
| POST | `/api/admin/site/publish` | owner | черновик → опубликован, прежняя версия → история |
| GET | `/api/admin/site/versions` | editor+ | список версий: кто, когда, что поменял |
| POST | `/api/admin/site/rollback/{version}` | owner | откат |
| POST | `/api/admin/uploads` | editor+ | загрузка картинки (требования — [[ТЗ Кибербезопасность]] SEC-07) |

5. Страницы рендерятся на сервере из `site.json` по шаблонам фронтенда (договориться с [[ТЗ Frontend]] FE-02). `/api/publish` с целым HTML — удалить после переезда.
6. Скрипт миграции: достать `site-data` из текущего `index.html` и записать `site.json`; картинки base64 — в файлы.

**Готово, когда:**
- [ ] Бот и сайт считают цену из одного файла; тест: поменяли цену через API → бот считает по новой без перезапуска.
- [ ] В коде нет `SITE_DATA`-регулярки и `DEFAULT_PRICING`.
- [ ] Неверный JSON отклоняется с понятной ошибкой на русском и указанием поля.
- [ ] Хранятся минимум 50 версий; откат работает.
- [ ] Миграция текущего сайта проходит без потерь (сравнение до и после в тесте).

### BE-02 · Учётные записи, сессии, роли, 2FA

**Зачем.** Один `ADMIN_PASSWORD` открывает всё: публикацию любого HTML на главном домене и рассылку всем подписчикам. Пароль ходит в каждом запросе в `Authorization: Bearer`. Подробные требования — [[ТЗ Кибербезопасность]] SEC-01.

**Что сделать.**
1. Таблица `users`: логин, хеш пароля (argon2id), секрет TOTP (зашифрован ключом из `.env`), роль, `telegram_user_id`, `disabled`, даты.
2. Роли:

| Роль | Кто | Что может |
| --- | --- | --- |
| `owner` | владелец | всё, включая пользователей, публикацию и рассылку |
| `editor` | контент-менеджер | черновики контента, загрузки, просмотр заявок |
| `manager` | менеджер проектов | заявки и проекты в CRM (BE-04) |
| `developer` | программист | свои проекты в CRM: этапы, тестовый адрес, комментарии |
| `viewer` | — | только просмотр |

3. Вход: `POST /api/auth/login` (логин + пароль) → `POST /api/auth/2fa` (TOTP) → cookie сессии `HttpOnly; Secure; SameSite=Strict; Path=/`, срок 12 ч, продление при активности, принудительный выход через 7 дней.
4. Сессии в базе (`sessions`: id-хеш, user_id, создана, последняя активность, IP-ключ, user-agent). `POST /api/auth/logout`, `GET /api/auth/me`, «выйти со всех устройств».
5. CSRF: для изменяющих запросов — заголовок `X-CSRF-Token` (double-submit) плюс проверка `Origin`.
6. Первый `owner` создаётся командой `python -m app.users create --role owner`. Сброс 2FA — тоже из консоли.
7. `/api/news` перевести на сессии; для машин — API-ключи с ролью и сроком (`api_keys`, в базе только хеш).
8. **Бот:** админ определяется по `from_user.id`, а не по `chat.id` (сейчас `app/bot.py:126`). Группа в `ADMIN_CHAT_IDS` остаётся только каналом для уведомлений; команды `/post`, `/forget`, `/last`, `/stats` принимаются от пользователей, у которых в `users` указан `telegram_user_id`.
9. `ADMIN_PASSWORD` убрать после миграции (переходный период 2 недели с предупреждением в логе).

**Готово, когда:**
- [ ] Без сессии все `/api/admin/*` отвечают 401, с ролью ниже нужной — 403 (тест на каждый маршрут).
- [ ] Пароль и TOTP нигде не хранятся в открытом виде; в `localStorage` и `sessionStorage` ничего секретного.
- [ ] 5 неверных попыток на логин → пауза 15 минут (на логин и на IP), плюс общий лимит на все попытки входа.
- [ ] Участник группы-уведомлений без своей учётки не может выполнить `/post` (тест).

### BE-06 · База: WAL, миграции, бэкапы

**Что сделать.**

**Готово, когда:**

- [ ] Бэкапы на сервере и вне его зашифрованы.

## P1

### BE-04 · Мини-CRM: заявки и проекты в работе

**Зачем.** У заявки сейчас есть только `delivered`. Нельзя понять, кто взял заявку, что ответили клиенту, сколько заявок стали договорами. После договора программисты ведут проект по 5 шагам с сайта (договор → прототип → дизайн и разработка → запуск), но система об этом ничего не знает.

**Что сделать.**
1. **Заявки.** Поля `orders`: `status` (`new` → `in_progress` → `quoted` → `won` | `lost` | `spam`), `assignee_id`, `amount_uzs` (сумма договора), `lost_reason`, `source` (сайт, бот, канал из UTM — см. BE-09), `updated_at`. Таблица `order_events`: история смены статусов и комментарии.
2. **Проекты.** Заявка в статусе `won` становится проектом (`projects`): ответственный программист, команда, этапы `contract` → `prototype` → `development` → `launch` → `support`, у каждого этапа плановая и фактическая дата, ссылка на результат (прототип, тестовый адрес, рабочий сайт). Плановые даты по умолчанию — из срока в ТЗ.
3. **Telegram.** В уведомлении о заявке — кнопки «Беру», «Отправил КП», «Договор», «Отказ», «Спам»: нажатие меняет статус, пишет в историю и обновляет сообщение. Программисту — уведомление, когда его назначили на проект.
4. **Напоминания.** Заявка в `new` дольше 4 рабочих часов; этап проекта просрочен на 2+ дня — сообщение ответственному и владельцу.
5. **API:** `GET /api/admin/orders?status=&from=&to=&q=` (пагинация курсором), `GET/PATCH /api/admin/orders/{id}`, `POST /api/admin/orders/{id}/comments`, `GET /api/admin/projects`, `PATCH /api/admin/projects/{id}/stages/{stage}`, экспорт CSV (owner, с записью в журнал). Программист видит только свои проекты.
6. **По желанию владельца (P2):** страница статуса для клиента по секретной ссылке — этапы, даты, ссылки на прототип и тестовый адрес. Без контактов и сумм.

**Готово, когда:**
- [ ] Статус заявки меняется и из Telegram, и из админки; история видна в обоих местах.
- [ ] `/stats` показывает конверсию «заявка → договор», сумму договоров за 30 дней и число просроченных этапов.

2. `ChatPrefs` — таблица `chat_prefs (chat_id, lang, currency, updated_at)`.
3. После перезапуска бот продолжает с того же шага.

**Готово, когда:**

### BE-07 · Здоровье, метрики, логи

**Что сделать.**

4. Внешний мониторинг доступности (UptimeRobot или аналог) на `/api/health` с тревогой в Telegram.

**Готово, когда:**

### BE-09 · Приём событий аналитики

Делается по плану событий из [[ТЗ Data Engineer]] (DE-01).

1. `POST /api/event` принимает пачку событий: `[{name, ts, session, props}]`, до 20 за раз, до 4 КБ. Имена и свойства проверяются по списку из плана; неизвестное отбрасывается.
2. Таблица `events_raw` (отдельная база `analytics.sqlite3`): время, `session` (случайный id вкладки, без cookie), имя, свойства JSON. **Без IP, user-agent и контактов.** Класс устройства (`mobile`/`desktop`) присылает фронт.
3. Текущие суточные счётчики `events` оставить, пока DE не переведёт `/stats` на новые таблицы.
4. Бот: метка из deep-link `/start <payload>` сохраняется в `chat_sources (chat_id, first_source, first_seen)`; заявка из бота получает `source` из неё и псевдоним чата (`HMAC` от `chat_id`, секрет в `.env`) — для связки «чат → заявка → договор».
5. Ссылки в новостях — через `/r/{news_id}` (счётчик кликов, редирект 302 только на сохранённый URL).
6. Лимит: 60 событий в минуту с IP-ключа (как сейчас — без записи IP).

### BE-11 · CI, линтер, staging

1. GitHub Actions: на каждый PR — `ruff check`, `ruff format --check`, `mypy app` (сначала мягко), `python -m unittest`, `pip-audit`.
2. Зависимости: `requirements.in` → `pip-compile --generate-hashes` → `requirements.txt` с хешами; Dependabot раз в неделю.
3. Staging: второй сервис на том же или отдельном VPS, свой бот (`@codexlab_test_bot`), свой `.env`. Деплой из ветки `main` — сначала на staging.

### BE-12 · Сроки хранения и удаление данных

Требования — [[ТЗ Кибербезопасность]] SEC-09.

1. Ежедневная задача очистки:
   - заявки в статусе `lost` или `spam` — удалять контакты через 12 месяцев (ТЗ без контактов остаётся для статистики);
   - отписавшиеся подписчики — удалять имя через 30 дней;
   - `events_raw` — 13 месяцев.
2. `/forget` расширить: по номеру заявки, по телефону или Telegram — удаляет заявки и подписку этого человека (с подтверждением).
3. Выгрузка данных по запросу человека: всё, что хранится о телефоне или chat_id, — JSON (owner, запись в журнал).
